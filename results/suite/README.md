# Scalable suite — highest N solved

Runs of `scripts/run_suite.jl` over the three families generated by
`benchmarks/generate_suite.jl`, every spec declaring its own grammar in the `synth-fun`
body. **Every solution counted here was re-verified independently** through the
all-or-nothing counterexample query (`independent full-spec verification: PASS`); no run
produced a FAIL.

Hardware: Apple M3, 24 GB, macOS 27.0.1, Julia 1.13.1 (aarch64), Z3 4.16.0 via Z3.jl
1.0.4, HerbSearch 1.0.2. Up to four cells ran concurrently, and at that level contention
is negligible — array_search_2/3/4 took 12.6/1.1/17.8 s under four concurrent cells
against 12.7/1.0/17.5 s under three.

**Timing caveat for the `*_rt120.*` cells.** They ran while two processes wedged on
piecewise_10 were still spinning at 100 % CPU (they cannot be interrupted — see the
stall section), so five CPU-bound processes were live and the earlier contention
measurement does not cover them: array_search_4/5/6 take 27.6/71.6/98.4 s there against
17.8/47.3/67.4 s in the uncontended cell. Compare *reach* across those cells, not times.
The round-length result in Result 1 is a reach gain, which contention can only have
worked against, so it is unaffected.

Protocol: `--problem-time 300` per problem, rounds bounded by `ROUND_ENUM=200000` and by
`--round-time` where stated (**this matters more than anything else here — see Result 1**),
`--regime chained` (seed transfer between consecutive problems), climb stops after two
consecutive failures. Per-problem rows are in the `*.csv` files, written as each problem
finishes; `scripts/summarise_suite.jl` regenerates the table below from them.

Solution sizes scale very differently across the families, which is the point of having
more than one: array_search grows linearly (16 → 61 nodes from N=2 to N=11, one `ite`
per branch), while max_N doubles at every step (21 → 196 nodes from N=3 to N=6) because
each solution embeds the previous one twice.

## Result 1 — recombination frequency is the strongest control, and its best setting follows the solution's compositional depth

A round boundary is the only place the bank re-seeds: `select_seeds` hands the next round
its best composite building blocks as **cost-1 atoms**, which is how a search bounded at
`max_cost = 6` reaches a 1236-node program at all. One long round never re-seeds, so it
keeps exploring at its original cost horizon; short rounds climb the compositional ladder
once per boundary.

Same spec, same grammar (d0s), same equivalence mode (`constraint`), same 300 s
per-problem budget — only the round length differs:

| rounds | max_7 | max_8 | max_9 | max_10 |
|---|---|---|---|---|
| one 300 s round | 230.2 s | ✗ (best 8/9) | ✗ (best 9/10) | — |
| 120 s rounds | **124.0 s** | **131.7 s** | **230.9 s** | ✗ (best 10/11) |

Two extra problems and roughly half the time at equal N. Measured against the other axes
in this document — grammar redundancy worth ~10 % in time and nothing in reach,
granularity beyond `split` worth nothing, equivalence mode worth one step — round length
is the strongest control by a clear margin.

This also closes the comparison with `../max_n_climbs/`, which recorded max_10 at the
same 300 s budget: those runs used `ROUND_TIME=120`, and `run_suite.jl` had been handing
the whole budget to a single round. Nothing about the hardware or the specs was involved.
Short rounds recover max_7 → max_9 here; the last step to max_10 sits inside the
reproducibility band `../max_n_climbs/README.md` documents for N ≥ 8, where identical
commands disagree because *where the timer cuts a round* changes what gets banked.

Across every max_N cell the failing problem ends one constraint short — 8/9, 9/10, 10/11,
11/12 — never further behind. The search reliably assembles all but the last obligation,
which is the shape you would expect if the missing step is one more recombination.

### …but the same change costs array_search four steps

Run back to back, same load, uniform sampling, nothing else different:

| N | one 300 s round | 120 s rounds |
|---|---|---|
| 2 – 7 | 12.1 / 1.1 / 19.3 / 51.5 / 72.8 / 108.8 s | 11.3 / 1.0 / 18.6 / 49.8 / 70.6 / 106.1 s |
| 8 | **190.4 s ✓** | ✗ (best 8/9) |
| 9 – 11 | 138.3 / 190.7 / 275.9 s ✓ | — |
| highest | **11** | **7** |

The per-problem times agree to within a few percent up to N=7, so this is not contention.
The split happens precisely at N=8, which needs ~190 s of *continuous* enumeration: a
120 s round boundary throws that progress away and restarts from seeds, and for this
family the restart never recovers.

### Why the two families disagree

`max_N`'s solution embeds the previous solution **twice** — sizes 21, 46, 96, 196, 476,
1236 — so a solved max_{N-1} re-seeded as a cost-1 atom is most of max_N, and every extra
round boundary is another rung on the ladder. `array_search_N`'s solution is a flat `ite`
chain growing by 5 nodes a step — 16, 21, 26, …, 61 — with nothing to compose: it has to
be enumerated in one continuous sweep, and a round boundary only discards the sweep.

**For the write-up:** the partial-satisfaction score supplies the gradient, but the
*frequency of recombination* converts the gradient into reach, and its best setting is a
function of how compositional the target is — frequent re-seeding for deeply nested
targets, long uninterrupted rounds for shallow ones. This is the temporal instance of the
resolution pattern below, and the one with the largest effect in either direction
(+2 steps on max_N, −4 on array_search). Any figure quoted from this suite must state its
round length.

## Result 2 — spec granularity is what makes the method work

Three encodings of *the same function*, same grammar, same budget, same seed transfer;
only the number of `(constraint …)` clauses differs.

| granularity | constraints | highest solved |
|---|---|---|
| `conj` — one conjunction | 1 | **none** (fails max_3, which `split` solves in 2.1 s) |
| `split` — today's form | N+1 | **max_6** |
| `witness` — disjunction case-split | 2N | **max_6**, ~2× slower per problem |

With a single conjunctive constraint the score is 0 until the program is wholly correct,
so there is no gradient at all: the bank holds one cell, enumeration collapses to 316
candidates, and the best program after 32 rounds is `x1` at 0/1. This isolates
*specification decomposability* as the source of the method's reach, rather than the
bank-and-seeding machinery, which is identical across all three rows.

Going finer than `split` does not merely fail to help, it **costs three steps**. Under the
better round structure (Result 1), where `split` reaches max_9, `witness` still stops at
max_6:

| granularity | constraints | d0s, constraint, 120 s rounds |
|---|---|---|
| `conj` | 1 | none |
| `split` | N+1 | **max_9** |
| `witness` | 2N | max_6 |

Two costs compound: 2N Z3 checks per candidate instead of N+1, and a bank fragmented over
2^2N subset cells instead of 2^(N+1), which collapses less and leaves `combine` more to
chew through. The useful granularity is one clause per independently satisfiable
obligation — not as many clauses as possible.

## The pattern across Results 2-5 — every abstraction here is a resolution dial that fails at both ends

The four axes below look unrelated but behave identically, and this is the thing worth
building the write-up around:

| dial | too coarse | too fine |
|---|---|---|
| round length | long rounds on max_N: no re-seeding → loses 2 steps | short rounds on array_search: sweep discarded → loses 4 steps |
| spec granularity | `conj`: no gradient, score is 0 until perfect → solves nothing | `witness`: bank fragments, 2× the Z3 cost → loses 3 steps |
| equivalence mode | — | `constraint` where constants fill the cells → array_search_2 unsolvable |
| observational sample | `-9:9` on piecewise: needed guard indistinguishable → unsolvable at N=2 | literal-pinned on array_search: bank stops collapsing → loses 4 steps |
| grammar tier | — | `d0` vs `d0s`: redundant comparisons, ~10 % time, no reach |

Too coarse and distinct programs collapse into one bank cell, so the one the solution
needs is thrown away. Too fine and nothing collapses, so the bank bloats and `combine`
drowns. The method's reach is set by how close each dial sits to the resolution the
*problem* actually has — which is why these are per-family choices and why every reported
number has to name them.

## Result 3 — the equivalence mode is a per-family choice, not a tuning knob

`EQUIV=constraint` keys the bank by *which subset* of constraints a program satisfies,
keeping the smallest program per subset. Whether that abstraction helps or destroys the
search turns on one question: **can a constant occupy a subset cell?**

- In `max_N` it cannot — no constant satisfies `(>= y x_i)` for all inputs — so cells are
  earned by composites and the bank fills with usable building blocks. This mode is the
  strongest available here: max_7 against max_6 for `both`.
- In `array_search_N` it can: the literal `i` satisfies branch constraint `i+1` by
  itself. Every cell fills with a size-1 constant, `select_seeds` only promotes blocks of
  size > 1, so no composite seed is ever formed and rounds 2+ re-enumerate the same 130
  candidates with 100 % dropped as equivalent. **array_search_2, the smallest problem in
  the family, is unsolvable in this mode**, while `both` solves it in 12.6 s.
- `piecewise_N` is the same: each bracket's output constant satisfies that bracket alone.

So constraint-subset equivalence is a predicate abstraction that only pays off when its
granularity exceeds what a constant can achieve. Reporting a single mode across the suite
would have confounded this with problem difficulty.

## Result 4 — a redundant operator costs time, not reach

`d0` gives the guard nonterminal all four order comparisons; `d0s` gives it only `<` and
`>`. For max_N the other two are redundant, since ties do not change a maximum, so `d0s`
halves the guard space. It buys about 10 % in time at equal N (max_6 in 73.4 s against
95.5 s, max_7 in 230.2 s against 251.9 s) and **no extra reach at all** — both stop at
max_7 with the same 8/9 best on max_8.

This also settles a comparison against `../max_n_climbs/`, which recorded max_10 under
`EQUIV=constraint` at the same 300 s budget. `d0s` reproduces the grammar those runs used
(it is exactly the one hardcoded in `scripts/iterative_seeded_max.jl`), so the grammar is
not the difference. The remaining difference is round structure: those runs used
`ROUND_TIME=120` inside the 300 s cap, giving several re-seedings per problem, where
`run_suite.jl` hands the whole budget to one round. `--round-time` now exposes that knob
and `*_d0s_rt120.*` is the cell that tests it.

## Result 5 — the observational sample decides what the search can distinguish

The behavioural signature was computed on 32 uniform draws from a hardcoded `-9:9`.
piecewise thresholds are 10, 20, …, 110, so every guard true across that whole window —
`x < 10`, `x < 20`, and even the constant comparison `2 < 8` — hashed to a single bank
cell, and the guard a solution needs was discarded in favour of whichever arrived first.
**piecewise_2 was unsolvable for that reason alone**, stuck at 1/2 with a size-1 best
program. Sampling the spec's own literals and their lower neighbours instead
(`src/PartialSat/ObservationalSamples.jl`) solves piecewise_2 in 1.9 s and carried the
family to N=9. Specs with no integer literals — every max_N spec — reproduce the original
draws element for element, so the numbers in `../max_n_climbs/` stay comparable.

The same change is a **four-step loss** on array_search: N=11 under `SAMPLE_MODE=uniform`
against N=7 under `:literals`, at the same budget, and N=7 only just inside it at
299.9 s of 300 s. The mechanism is the one the mode is for — a finer sample distinguishes
more programs, so the bank collapses less and `combine` has more to work through — and
array_search gains nothing from the extra resolution because all of its behaviour already
lives inside `-9:9`. So the sample is a per-family axis like the equivalence mode, not a
bug with a fix: state which mode a number used. Both figures above are reproducible from
HEAD via `SAMPLE_MODE`.

## Caveat — piecewise_10 overruns its budget by 35×, inside library code

`guided_partial_search` checks its wall clock between *yielded* candidates. The bottom-up
iterator computes a signature for every combination it considers and yields only the
first of each equivalence class, so when the gate starts rejecting nearly everything the
iterator can spin without yielding at all. **piecewise_10 does exactly this**: 100 % CPU,
flat RSS (746 MB), no log line, against a 300 s per-problem cap.

It is an overshoot, not a deadlock. Run from scratch under a 60 s per-problem cap,
piecewise_10 completed its 3 rounds — after **2114 s**, 35× the budget it was given, with
the deadline never firing. So the work is finite and the search is not wedged in the
usual sense; the per-problem budget simply does not bound it, and a climb that hits such
a problem appears hung for as long as it takes. The earlier cells reported here as
"stalled" would presumably have finished too, given long enough.

What has been ruled out, each by a run that reproduced the stall anyway:

| suspect | test | verdict |
|---|---|---|
| e-graph pruning stage | `USE_EGRAPH=0` control (`*_noegraph.*`) | not the cause — stalls identically |
| a single unbounded Z3 query | 5 s per-query cap (`CSAT_TIMEOUT_MS`) | not the cause — stalls with the cap in place |
| a deadline the search never checks | deadline armed inside the signature hook | **never fires** — 9 min past it in one cell, and across 3 rounds of a 2114 s run |

The last row is the informative one. The hook is the only part of *our* code on that path,
and arming the deadline there does not interrupt the stall, so the spin is inside
HerbSearch's own `combine` machinery. Three runs stall at the identical point — enum
49000, best 9/10, 377 banked subsets — so it is deterministic, not a race.

Bounding it therefore needs something outside the search: run each problem in its own
process under an OS-level timeout, or a watchdog thread that can interrupt the iterator.
Until then `piecewise_9` is the family's honest high-water mark at a practical budget, and
every per-problem wall-clock figure in this document is a floor rather than a bound. The two instrumentation fixes made along the way (the Z3 cap and the
per-problem CSV append) are worth keeping regardless: without the latter, a killed cell
reported *none* of the eight problems it had solved and verified.
